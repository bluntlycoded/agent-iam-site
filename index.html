Where it breaks

Most agents run on borrowed authority.

An agent usually inherits a person's token or a shared API key. It can do whatever that credential allows, for as long as the credential lives, and nobody is asked first. Four failures follow from that.

No brakes

Runaway actions

An agent loops on a bad plan and keeps writing. By the time a person notices, the damage is done, because nothing sat between the decision and the call.

Keys that never expire

Standing access

The task finished last week. The key it used still works, and so does every copy of it in logs, configs and context windows.

Permissions that grow

Scope creep

One agent hands work to another and passes along everything it holds. Each hop is a chance for authority to widen rather than narrow.

One leak, every system

Blast radius

A single prompt injection or leaked secret reaches every system the credential touches. There is no boundary, so there is no limit.

02 · Control every action

Each call is decided inline, with people in the loop where it matters.

Requests go through an enforcement proxy and gateway. A Cedar policy decides each one, and risky actions wait for a person to approve them. Content guardrails score prompt injection, redact PII and secrets, and check what tools send back. Launched agents run in a Docker sandbox whose only way out is the proxy.

  • Cedar policy on every action, with human approvals
  • Injection scoring, PII and secret redaction, tool-response checks
  • RFC 8693 delegation where scope can only shrink
  • Kill switch, quarantine and owner offboarding

policy.cedar

// Money moves only with a person's approval
forbid (
  principal,
  action == Action::"payments.transfer",
  resource
)
unless { context.approved };

// Never act on content that looks injected
forbid (principal, action, resource)
when { context.injection >= 70 };

03 · Govern and prove

A record that holds up without taking our word for it.

Every decision lands in a tamper-evident ledger that independent witnesses co-sign. Exports verify offline, so an auditor can check them on their own machine. Evidence is mapped to the frameworks your reviewers already use.

  • Hash-chained audit ledger with independent witnesses
  • Exports that verify offline
  • Evidence mapped to EU AI Act, NIST AI RMF, OWASP LLM Top 10, OWASP Agentic and MITRE ATLAS

Anatomy of an agent

The same agent, before and after.

Five layers of a typical agent, and what changes when Agent IAM sits in front of it.

Layer Without With Agent IAM
Who it is
Uses someone else's login. Logs show a person or a shared key, not the agent.
Its own signed identity. A SPIFFE ID tied to an owner, model, config hash and tools.
What it sees
Everything in context. Secrets and personal data flow to the model and to every tool.
Redacted on the way through. PII and secrets are stripped; tool responses are checked too.
Who decides
The model does. An injected instruction becomes an action.
Policy does. Cedar rules and injection scores decide inline; people approve the risky calls.
What it reaches
Anything the key opens. Direct network access, long-lived credentials.
Only through the proxy. Sandboxed egress and delegated tokens that only narrow.
What's left after
Scattered logs. Easy to edit, hard to trust in a review.
A signed ledger. Witnessed, exportable, and checkable offline.
