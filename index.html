The problem

Most agents run on borrowed authority.

An agent usually inherits a person's token or a shared API key. It can do whatever that credential allows, for as long as the credential lives, and nobody is asked first. When something goes wrong, the logs name a person or a key, not the agent, and nobody can say who was responsible at that moment.

Where it breaks

No brakes

Runaway actions

An agent loops on a bad plan and keeps writing. By the time a person notices, the damage is done, because nothing sat between the decision and the call.

Keys that never expire

Standing access

The task finished last week. The key it used still works, and so does every copy of it in logs, configs and context windows.

Permissions that grow

Scope creep

One agent hands work to another and passes along everything it holds. Each hop is a chance for authority to widen rather than narrow.

One leak, every system

Blast radius

A single prompt injection or leaked secret reaches every system the credential touches. There is no boundary, so there is no limit.

Give each agent its own identity and a decision on every call, and each of these becomes something you can stop.

02 Control every action

Each call is decided inline, with people in the loop where it matters.

Agents sign every request. A Cedar policy decides it, content guardrails look inside it, and risky actions wait for a person. Tools act only on a fresh, signed "allowed" for exactly what they were asked to do.

  • Cedar policy on every action, with one-use human approvals the owner can't grant themselves
  • Injection scoring, PII and secret redaction, and checks on what tools send back
  • Launched agents run in a Docker sandbox whose only way out is the proxy
  • Kill switch for one agent, its subtree, or every agent with a given configuration
policy.cedarpublished · replayable

  action == Action::"payments.transfer",

// Never act on content that looks injected

  action == Action::"email.send",
  resource

Sandboxed launches

Each launch gets an internal Docker network with no route out, a gateway that holds the key, and a container with every capability dropped.

Keys stay with the proxy

The proxy adds provider keys from its own environment. The agent never holds an API key, and its own credential headers are dropped.

Undo and delay

Reversible writes are rewound on a kill. Risky sends wait in a delay queue and are cancelled if the agent is stopped first.

Rogue detection

Honeytokens and out-of-manifest calls kill at once. A burst of denials suspends the agent until two people release it.

MCP gateway

Every tools/call is decided first. The remote gateway refuses calls without a fresh receipt for that exact tool and arguments.

Framework hooks

LangGraph and CrewAI wrappers in the Python SDK decide and record each tool call without rewriting your agent.

03 Govern and prove

A record that holds up without taking our word for it.

Every decision, allowed or denied, is written to a hash-chained ledger before the answer goes out. Independent witnesses keep their own signed copies of its checkpoints, so even an insider holding every key can't quietly rewrite history.

  • Independent witnesses that refuse any history without a consistency proof
  • Offline audit with three public keys and the published policy
  • Evidence mapped to EU AI Act, NIST AI RMF, OWASP LLM Top 10, OWASP Agentic and MITRE ATLAS

Agent lifecycle

From first key to last request, every stage is enforced.

Agents are accounts with an owner and an end. When something changes, the next request already knows.

  1. Enrol

    The ID is a hash of the agent's key, its manifest and its creator. The root key signs a birth certificate.

  2. Launch

    Optional sandbox: internal network, a gateway holding the key, every call through the proxy.

  3. Act

    Each request is signed, decided and recorded before the answer goes out. Tools check the receipt.

  4. Suspend

    The next request is refused, measured at 14 ms. Automatic on an out-of-manifest tool or a burst of denials.

  5. Offboard

    When the owner leaves, their agents drop to reads until a successor claims them. SCIM from Okta or Entra ID can trigger it.

  6. Retire

    A revoked key or ID is never accepted again. Bringing an agent back takes two people and gives it a new ID.

Delegation · RFC 8693

Authority only ever shrinks.

When an agent hands work to another agent, it exchanges its token for a narrower one with OAuth 2.0 Token Exchange. The new token names who acted for whom in its act claim, carries a subset of the tools, and lives no longer than the one it came from.

  • Tokens narrowed to a scope and a task, carrying the agent's SPIFFE ID
  • Spawned agents stay accountable through their parents
  • Killing a parent retires its whole subtree
  • Standard metadata at /.well-known/oauth-authorization-server

Questions

Asked before every pilot.

If yours isn't here, ask us on the demo call.

Do we have to send our data to you?

No. Agent IAM is a single binary you run on your own machines. The dashboard loads nothing from elsewhere, and the ledger stays in your file system or your Postgres.

How much do we have to change in our agents?

Often only a base URL. Agents launched in the sandbox send tool and model calls to a gateway as plain HTTP; the gateway signs, asks for a decision and forwards. MCP clients point at id mcp, and LangGraph and CrewAI apps wrap their tools with the Python SDK.

What stops an agent from going around the proxy?

In a sandboxed launch the agent's container sits on an internal Docker network with no route out. Only the gateway can reach the service and the proxy, and the gateway holds the key, not the agent.

How fast is the kill switch?

Suspending or revoking an agent blocks its very next request. In our measurements a suspended agent was denied 14 ms after the suspension, and all 100 agents of an offboarded owner were denied within 0.8 s.

Why post-quantum signatures?

An audit record has to stay trustworthy for years. Agent, ledger and witness signatures use ML-DSA-65 and the root key uses SLH-DSA, so records signed today still hold up later. Classical and hybrid modes are available too.

Why should an auditor trust the ledger if we run it?

They don't have to. Independent witnesses keep signed copies of every checkpoint, agents keep signed receipts, and the offline verifier replays every decision against the published policy. If records were cut or rewritten, it names who must have misbehaved.

Does this make us compliant with the EU AI Act?

No product does that on its own. Agent IAM gives you evidence mapped to EU AI Act, NIST AI RMF, OWASP and MITRE ATLAS controls to support your assessment.
